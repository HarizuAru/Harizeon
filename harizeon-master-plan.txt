01. THESIS
================================================================================

AWS won because it turned capital expenditure into an API call. You no longer
bought a server; you called RunInstances.

Cybersecurity has not had that moment for small teams. It is still sold the way
servers were sold in 2004: annual contracts, sales calls, per-seat minimums,
onboarding engineers, six-figure floors. A 4-person startup in Kuala Lumpur that
needs a WAF, a vulnerability scan, and a place to put its secrets has three bad
options: enterprise tools they cannot afford, free tools they cannot operate, or
nothing.

HARIZEON'S BET:
  Package security capabilities as metered, self-serve, API-first services behind
  one console and one bill. No sales call. No contract. Sign up, verify your
  domain, get a scan in four minutes, pay for what you used.

ONE-LINE PITCH:
  "Harizeon is the security control plane for teams too small to have a security
  team."

WHAT YOU ARE NOT BUILDING:
  - Not a next-gen EDR. Endpoint agents are a multi-year, multi-team problem.
  - Not a SOC. Humans in a room monitoring alerts does not scale for a solo founder.
  - Not a compliance certification body. You produce evidence, you do not certify.
  - Not novel detection research. You are an integration and UX company that
    wraps proven open-source engines in an operable product. Say this out loud
    and stop feeling bad about it — AWS did not invent the hypervisor either.

WHY YOU SPECIFICALLY CAN BUILD THIS:
  Netcentric Computing coursework = networking + cloud + security fundamentals.
  AWS CCP = you already think in the service/console/billing mental model this
  product copies. Malaysia = an underserved SME market with a real data
  protection law (PDPA) and almost no affordable local tooling.

================================================================================

6.1 PRINCIPLE
  Split CONTROL PLANE (the console, the API, billing, state — must be reliable,
  boring, always up) from DATA PLANE (the scanners — untrusted, resource-hungry,
  disposable, isolated). This is the single most important architectural
  decision in the document. AWS does this. Copy it.

6.3 WHY WORKERS ARE ISOLATED
  A scanner parses hostile input: attacker-controlled HTTP responses, TLS certs,
  banners. Parsers have bugs. Assume a worker can be compromised. Therefore:
   - workers hold NO database credentials and NO customer secrets
   - workers receive a narrowly-scoped job payload and a one-time result token
   - workers run in a separate network segment with no route to the control plane
     database or to other tenants' jobs
   - one job per container, hard CPU/memory/time limits, destroyed after
   - egress from workers is logged; internal RFC1918 ranges blocked by default so
     a malicious "asset" cannot pivot you into your own infrastructure (SSRF)

6.4 SCAN JOB LIFECYCLE (state machine)

  QUEUED -> CLAIMED -> RUNNING -> [COMPLETED | FAILED | TIMEOUT | CANCELLED]
     ^                    |
     +----- retry (max 2, exponential backoff) -----+

  Every transition writes to scan_events with a timestamp. The progress bar in
  the UI is just a projection of this table. Do not fake progress.

  A scan is decomposed into PHASES so the UI can show something real:
    1. verify        (confirm ownership token still valid)
    2. discover      (subdomains, DNS, WHOIS)
    3. resolve       (hostnames -> IPs, dedupe, respect scope rules)
    4. probe         (port scan, service fingerprint)
    5. inspect       (TLS grade, headers, tech fingerprint)
    6. test          (template-based web vulnerability checks)
    7. normalize     (dedupe findings, assign severity, diff vs last scan)
    8. report        (materialize summary, trigger notifications)

6.5 SCANNING ENGINE SUPPLY CHAIN
  Do not write scanners from scratch. Wrap mature open-source engines and own the
  orchestration, normalization, storage, UX, and reporting. Check each project's
  licence before you ship commercially — some are GPL/AGPL and that affects how
  you may distribute; running them server-side as a service is generally the safe
  pattern, but read the licences yourself and get them reviewed before launch.

  Candidate engines by phase (evaluate, pick one per slot):
    discovery   : passive DNS sources, certificate transparency logs
    port probe  : a fast open-source port scanner with service detection
    TLS         : an open-source TLS configuration analyzer
    web checks  : a template-driven scanner with a community template repository
    dependency  : a container/SBOM vulnerability scanner (for v0.2 "code" scans)
    CVE data    : NVD feed + your own enrichment table, cached locally

  NORMALIZATION IS YOUR PRODUCT. Every engine emits a different shape. You define
  ONE finding schema (section 07) and map everything into it. This mapping layer
  is genuinely the most valuable code you will write in year one.

6.6 MULTI-TENANCY MODEL
  Single database, row-level tenancy on org_id. Every table that holds customer
  data carries org_id and every query goes through a repository layer that
  injects it. Do not rely on developers remembering a WHERE clause.
  Use PostgreSQL row-level security as a second net.
  Revisit dedicated-DB-per-tenant only when an enterprise customer pays for it.

6.7 ENVIRONMENTS
  local  -> docker compose, everything on one machine, seeded fake data
  stage  -> one small VPS, mirrors prod, scans only your own throwaway domains
  prod   -> control plane VPS(s) + separate worker VPS(s), same region
  No staging data in prod. No prod credentials on your laptop.

07. DATA MODEL
================================================================================

Written as logical tables. All tables: id (uuid), created_at, updated_at.
All tenant tables: org_id (fk, indexed, NOT NULL).

  orgs
    id, name, slug, plan_id, billing_status, country, currency,
    trial_ends_at, suspended_at

  users
    id, email (unique, citext), password_hash, name, email_verified_at,
    mfa_secret (nullable), last_login_at, locale ('en'|'ms')

  memberships                     -- built now even though MVP is 1 user/org
    id, org_id, user_id, role ('owner'|'admin'|'member'|'readonly'),
    invited_by, accepted_at

  api_keys
    id, org_id, name, prefix (visible, e.g. "hrz_live_a9f2"),
    hash (argon2 of the secret), scopes (jsonb array), last_used_at,
    expires_at, revoked_at
    -- store ONLY the hash; show the full key exactly once at creation

  audit_log                       -- append-only, never updated or deleted
    id, org_id, actor_type ('user'|'api_key'|'system'), actor_id,
    action ('asset.create','scan.start','apikey.revoke',...),
    target_type, target_id, ip, user_agent, metadata (jsonb)

  assets
    id, org_id, type ('domain'|'subdomain'|'ip'|'url'),
    value, parent_asset_id (nullable, for discovered subdomains),
    discovered_by ('manual'|'discovery'), first_seen_at, last_seen_at,
    is_active, tags (jsonb), criticality ('low'|'medium'|'high')

  asset_verifications
    id, org_id, asset_id, method ('dns_txt'|'http_file'|'meta_tag'),
    token, verified_at, last_checked_at, status ('pending'|'verified'|'failed'|'revoked')
    -- re-check periodically; a domain that changed hands must lose verification

  scans
    id, org_id, project_id, trigger ('manual'|'scheduled'|'api'|'webhook'),
    profile ('quick'|'standard'|'deep'), status, phase, progress_pct,
    started_at, finished_at, error_code, requested_by, engine_versions (jsonb)

  scan_targets
    id, scan_id, asset_id, status, result_summary (jsonb)

  scan_events                     -- the timeline / progress source of truth
    id, scan_id, phase, level ('info'|'warn'|'error'), message, at

  findings
    id, org_id, asset_id, scan_id (first seen), fingerprint (unique per org),
    title, description, severity ('info'|'low'|'medium'|'high'|'critical'),
    cvss_score, cve_ids (text[]), cwe_id, category,
    evidence_ref (object storage key), remediation,
    status ('open'|'acknowledged'|'fixed'|'false_positive'|'accepted'),
    status_reason, first_seen_at, last_seen_at, resolved_at, assigned_to
    -- FINGERPRINT is critical: hash(asset + check_id + location) so the same
    -- issue across 50 scans is ONE finding with a history, not 50 rows.

  finding_events
    id, finding_id, actor_id, from_status, to_status, note, at

  notification_channels
    id, org_id, type ('email'|'slack'|'webhook'|'discord'), config (jsonb,
    secrets encrypted), enabled, min_severity, verified_at

  schedules
    id, org_id, project_id, cron, profile, timezone, next_run_at, enabled

  plans
    id, code ('free'|'starter'|'growth'|'scale'), price_myr_month,
    limits (jsonb: max_assets, scans_per_month, retention_days, seats)

  subscriptions
    id, org_id, plan_id, provider, provider_ref, status, current_period_end,
    cancel_at_period_end

  usage_records                   -- metering, one row per billable unit
    id, org_id, metric ('scan.standard','asset.monitored','report.pdf'),
    quantity, unit_cost, occurred_at, invoice_id (nullable)

  invoices
    id, org_id, number, period_start, period_end, subtotal, tax, total,
    currency, status, pdf_ref, paid_at

  reports
    id, org_id, project_id, type ('executive'|'technical'|'compliance'),
    generated_at, period_start, period_end, file_ref, generated_by

INDEXING NOTES
  findings: (org_id, status, severity), (org_id, asset_id), unique(org_id, fingerprint)
  scan_events: (scan_id, at)
  audit_log: (org_id, created_at desc), partition by month once it grows
  usage_records: (org_id, occurred_at), (invoice_id)

RETENTION
  Raw scan evidence: 90 days on paid, 14 days on free, then delete from object
  storage but keep the finding record. Evidence is the expensive part.

08. API DESIGN
================================================================================

Base: https://api.harizeon.com/v1
Auth: Authorization: Bearer hrz_live_xxxxx   (API key)  OR session cookie (console)
Format: JSON. Errors follow one shape, always:

  { "error": { "code": "asset_not_verified",
               "message": "Asset must be verified before scanning.",
               "doc_url": "https://docs.harizeon.com/errors/asset_not_verified",
               "request_id": "req_01HZ..." } }

ENDPOINTS (MVP surface — keep it this small)

  POST   /auth/signup
  POST   /auth/login
  POST   /auth/logout
  POST   /auth/verify-email
  POST   /auth/password/reset

  GET    /org
  PATCH  /org
  GET    /org/members
  POST   /org/members/invite

  GET    /api-keys
  POST   /api-keys                  -> returns secret ONCE
  DELETE /api-keys/{id}

  GET    /assets                    ?type=&status=&q=&page=
  POST   /assets                    { type, value, criticality, tags }
  GET    /assets/{id}
  PATCH  /assets/{id}
  DELETE /assets/{id}
  POST   /assets/{id}/verification  -> { method } returns token + instructions
  POST   /assets/{id}/verification/check -> re-check now

  GET    /scans                     ?status=&asset_id=&page=
  POST   /scans                     { asset_ids[], profile }
  GET    /scans/{id}
  GET    /scans/{id}/events         (supports Server-Sent Events for live view)
  POST   /scans/{id}/cancel

  GET    /findings                  ?severity=&status=&asset_id=&since=&page=
  GET    /findings/{id}
  PATCH  /findings/{id}             { status, status_reason, assigned_to }
  GET    /findings/{id}/evidence    -> signed short-lived URL

  GET    /schedules
  POST   /schedules
  PATCH  /schedules/{id}
  DELETE /schedules/{id}

  GET    /channels
  POST   /channels
  POST   /channels/{id}/test
  DELETE /channels/{id}

  POST   /reports                   { type, period, asset_ids[] } -> async job
  GET    /reports/{id}              -> status + download ref

  GET    /usage                     ?period=
  GET    /billing/subscription
  POST   /billing/checkout-session
  GET    /billing/invoices

  GET    /health                    (public, no auth)

CONVENTIONS
  - Pagination: cursor-based. { data: [...], next_cursor: "...", has_more: bool }
  - Idempotency-Key header honoured on all POST that create billable work.
  - Rate limits returned in headers: X-RateLimit-Limit / -Remaining / -Reset.
  - Every response carries X-Request-Id. Log it. Support depends on it.
  - Webhooks OUT are signed: HMAC-SHA256 of the raw body with the channel secret,
    in X-Harizeon-Signature, plus a timestamp to prevent replay.
  - Versioning: /v1 in the path. Never break v1. Add v2 when you must.

10. UI / UX DESIGN SYSTEM — PURE BLACK AND WHITE
================================================================================

10.1 PHILOSOPHY
  Colour is the laziest way to encode severity. Removing it forces hierarchy
  through type weight, size, spacing, borders, and fills — which is more
  accessible, prints perfectly, and looks like an instrument rather than a toy.
  Constraint is the brand.

10.2 TOKENS

  --hz-black:       #000000
  --hz-white:       #FFFFFF
  --hz-grey-900:    #111111   text on white, secondary
  --hz-grey-700:    #3A3A3A   muted text
  --hz-grey-500:    #767676   disabled, placeholder (lowest AA-safe on white)
  --hz-grey-300:    #C8C8C8   borders, dividers
  --hz-grey-100:    #F2F2F2   subtle fill, table zebra, code background
  THAT IS THE ENTIRE PALETTE. No blue. No red. Not even for destructive actions
  — destructive is communicated with a solid black fill plus a confirm step.

  Dark mode = exact inversion. Black canvas, white text, greys mirrored.
  Provide a toggle; respect prefers-color-scheme.

10.3 TYPOGRAPHY
  Display / headings : a grotesk sans (e.g. Inter or Helvetica Neue), tight
                       tracking, weights 500/700 only.
  Body               : same sans, 400/500.
  Data / code / IDs / numbers / domains / timestamps : ALWAYS monospace
                       (e.g. JetBrains Mono or IBM Plex Mono).
  The mono/sans split is the core visual signature. Prose is sans. Facts are mono.

  SCALE (rem, 16px base)
    display  2.50  700  -0.02em
    h1       2.00  700  -0.02em
    h2       1.50  600
    h3       1.25  600
    body     1.00  400   line-height 1.55
    small    0.875 400
    micro    0.75  500   uppercase  +0.08em tracking (labels, table headers)
    mono     0.875 400   line-height 1.5

10.4 SPACING + GEOMETRY
  4px base unit. Use 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64.
  Border radius: 0 everywhere. Sharp corners. One exception: 2px on chips if a
  fully square chip reads as broken. Decide once, stay consistent.
  Borders: 1px solid var(--hz-grey-300). 2px solid black for emphasis/focus.
  Shadows: none. Elevation is expressed with borders and background inversion.

10.5 COMPONENT RULES
  BUTTON
    primary     black fill, white text, 1px black border, hover -> grey-900
    secondary   white fill, black text, 1px black border, hover -> grey-100
    ghost       transparent, black text, underline on hover
    destructive black fill + the word is explicit ("Delete permanently") + a
                confirm dialog that requires typing the resource name
    disabled    grey-300 border, grey-500 text, no fill
    heights     32 / 40 / 48. Never rounded.
  INPUT
    1px grey-300 border, black text, grey-500 placeholder,
    focus: 2px black border (no glow), error: 2px black border + a bold
    monospace error line beneath prefixed with "ERROR: "
  TABLE
    1px grey-300 dividers, micro uppercase headers, zebra on grey-100,
    hover row -> grey-100, selected row -> black left border 2px.
    All identifiers, values, and timestamps in mono.
  CHART
    Never colour. Distinguish series by: line weight (1px/2px/3px), dash
    pattern (solid/dashed/dotted), fill pattern (solid/hatch/dots), and direct
    labels at the end of each line. Always direct-label; legends are a failure.
  SEVERITY (the one thing that must be instantly readable)
    CRITICAL  solid black chip, white uppercase bold text, prefix [!!!]
    HIGH      solid black chip, white uppercase text, prefix [!!]
    MEDIUM    white chip, 2px black border, black uppercase text, prefix [!]
    LOW       white chip, 1px grey-300 border, grey-700 text, prefix [-]
    INFO      no chip, grey-500 text, prefix [i]
    Always pair the chip with the word AND the bracket prefix. Three redundant
    channels means it survives greyscale printing, low vision, and screenshots.

10.6 MOTION
  Durations 120ms / 200ms only. Ease-out. Animate opacity and transform only.
  Loading = skeleton blocks in grey-100, never spinners, except the scan phase
  rail which uses a blinking mono cursor. Respect prefers-reduced-motion.

10.7 ACCESSIBILITY (non-negotiable, and easier in monochrome)
  Contrast: body text is black on white = 21:1. Never put text below grey-500
  on white. Focus rings are visible 2px black (white in dark mode) and never
  removed. Every icon has a text label. Full keyboard navigation: j/k to move
  in the findings list, / to focus search, g+f to go to findings.
  Target AA minimum, AAA for body text.

10.8 VOICE AND COPY
  Direct, technical, unhype. Never "Oops!" Never exclamation marks.
  Bad:  "Uh oh! Something went wrong 😬"
  Good: "Scan failed at phase PROBE: connection timed out after 30s. Retry?"
  Severity language is literal. Never say "urgent" when you mean "high".
  Bilingual: full EN and BM strings from day one. Store in i18n files, not
  hardcoded. BM matters for the local SME market and nobody else does it.

11. SECURING HARIZEON ITSELF
================================================================================

You are a security company. One breach and the company is over. This section is
not optional polish.

  IDENTITY
    Argon2id password hashing. TOTP MFA available from launch, enforced for
    owners on paid plans. Session cookies: HttpOnly, Secure, SameSite=Lax,
    rotate on privilege change, absolute timeout.
  SECRETS
    Nothing in the repo. Environment injection or a managed secret store.
    Customer notification-channel secrets encrypted at rest with an envelope
    key. Rotate the master key annually and document how.
  API KEYS
    Hash at rest. Prefix visible for identification. Scoped. Revocable.
    Show once. Detect and alert on keys committed to public repos (later).
  TENANCY
    Row-level security in Postgres as a backstop. Every integration test
    includes a cross-tenant access assertion. Write that test on day one.
  SSRF / SCANNER ABUSE  (your biggest technical risk)
    Workers resolve targets and block RFC1918, loopback, link-local, and cloud
    metadata endpoints unless explicitly allowlisted for an enterprise
    on-prem case. Block redirects to those ranges too. Re-resolve after redirect
    (DNS rebinding). Log every outbound connection a worker makes.
  RATE LIMITING
    Per-key and per-org. Scan concurrency caps per plan. Global circuit breaker
    so one customer cannot exhaust the worker pool.
  SUPPLY CHAIN
    Pin every dependency. Lockfiles committed. Automated dependency scanning on
    every PR. Pin scanner engine versions and record them in scans.engine_versions
    so a finding is reproducible.
  LOGGING
    Structured JSON, request_id on everything, PII minimized, secrets redacted
    by a logging filter (test the filter). Ship logs off-box. 90-day retention.
  BACKUPS
    Automated daily Postgres backups, encrypted, stored in a different provider
    than production. TEST A RESTORE MONTHLY AND WRITE THE DATE DOWN. An untested
    backup is a rumour.
  RESPONSIBLE DISCLOSURE
    security.txt at /.well-known/security.txt, a /security page, a published
    response SLA, and a hall of fame. You will get reports. Answer them well;
    it is free marketing in exactly your market.
  YOUR OWN MEDICINE
    Harizeon scans harizeon.com on a schedule and the score is on the /security
    page publicly. This is the most persuasive marketing asset you will ever have.

12. LEGAL, ETHICAL, AND AUTHORIZATION GATES
================================================================================

READ THIS TWICE. This is the section that decides whether Harizeon is a company
or an incident.

12.1 THE CORE RULE
  Harizeon performs active testing ONLY against assets whose control the customer
  has cryptographically demonstrated. Verification is not a UX step you can skip
  for "trusted" users, enterprise deals, or demos. There is no bypass flag. If
  you build a bypass flag, someone will use it, and it will be you at 2am.

12.2 VERIFICATION MECHANICS
  - DNS TXT record containing a per-asset random token, OR
  - a file at /.well-known/harizeon-verification.txt containing the token, OR
  - a meta tag on the root document (weakest, offer last).
  - Re-verify on a schedule (weekly). Domains change hands. If re-verification
    fails, scanning pauses automatically and the customer is notified.
  - IP ranges require a stronger path: reverse DNS plus a signed authorization
    form, reviewed manually. Do not automate IP-range authorization in v1.

12.3 MALAYSIAN AND REGIONAL CONTEXT
  Unauthorized access to computer material is a criminal offence in Malaysia
  under the Computer Crimes Act 1997. Personal data handling is governed by the
  Personal Data Protection Act 2010 (amended in recent years — check the current
  text). Other jurisdictions have their own equivalents, and a scan initiated in
  Malaysia may touch infrastructure abroad.

  ACTION ITEMS, not reading material:
    [ ] Engage a Malaysian lawyer before public launch. Budget for it. This is
        not the place to be frugal.
    [ ] Have them review: Terms of Service, Acceptable Use Policy, the
        authorization warranty clause, the liability cap, and your PDPA
        obligations as a data processor/controller.
    [ ] Get written advice on scanning cross-border targets.
    [ ] Register the business properly (SSM). Do not sign customers as a person.
    [ ] Obtain professional indemnity / cyber liability insurance before your
        first paying customer. Ask specifically whether it covers claims arising
        from a scan against a third party.
  Nothing in this document is legal advice. I am not a lawyer.

12.4 ACCEPTABLE USE POLICY — CLAUSES THAT MUST EXIST
  - Customer warrants it owns or is contractually authorized to test each asset.
  - Customer indemnifies Harizeon for claims arising from assets it added.
  - Harizeon may suspend without notice on suspected unauthorized targeting.
  - No use of Harizeon output to attack systems.
  - Harizeon logs all scan activity and will cooperate with lawful requests.

12.5 ABUSE DETECTION (build these into v1, they are cheap)
  - Flag accounts that add many unrelated domains quickly.
  - Flag failed-verification rates above a threshold.
  - Flag targets on government / financial / critical-infrastructure TLDs and
    domain lists for manual review before any active phase runs.
  - Keep an internal blocklist of assets that must never be scanned.
  - Abuse inbox monitored. Published. Answered within 24h.

12.6 DATA PROTECTION
  Scan evidence may contain personal data incidentally. Therefore: minimize what
  you store, mask by default in the UI, encrypt at rest, delete on schedule,
  honour deletion requests within 30 days, publish a data processing addendum,
  and keep a register of sub-processors (your hosting provider, email provider,
  payment provider).

20.3 SEVERITY DEFINITIONS (publish these; customers will ask)
  CRITICAL  Exploitable now, leads to data exposure or system compromise,
            no preconditions. Fix today.
  HIGH      Exploitable with minor preconditions, or exposes sensitive config.
            Fix this week.
  MEDIUM    Meaningful weakening of security posture; needs chaining to exploit.
            Fix this month.
  LOW       Best-practice deviation with limited direct impact. Fix when convenient.
  INFO      Observation, no action required. Context only.

20.4 SECURITY SCORE (be transparent about the formula or do not show a score)
  Start at 100. Subtract per open finding, weighted by severity and age, capped
  per category so one noisy category cannot zero the score. Publish the exact
  weights on a docs page. An opaque score is a trust liability; a transparent
  one is a feature.
